# Power Pages site settings & environment variables

How this repo tracks Power Pages configuration, what's intentionally excluded from git, and the environment variables currently in use.

## Source control: what's tracked and why

The site's config-as-code lives under `vmbso-spa-v2/.powerpages-site/`, downloaded/uploaded via PAC CLI (`download.ps1`, `npm run deploy`). Not everything in that folder should be tracked:

| Path | Tracked? | Reason |
|---|---|---|
| `.powerpages-site/site-settings/*.sitesetting.yml` | ✅ Yes | Config-as-code — the actual source of truth for site behavior. |
| `.powerpages-site/page-templates/`, `web-templates/`, `web-roles/`, `table-permissions/`, etc. | ✅ Yes | Hand-authored/maker-configured components, not regenerated by a build. |
| `.powerpages-site/.portalconfig/manifest.yml` | ✅ Yes | Delete-tracking manifest — needed regardless of which environment you're deploying to. |
| `.powerpages-site/.portalconfig/*-manifest.yml` (e.g. `vmbso-customerportal-dev...-manifest.yml`) | ❌ No | Per-environment, local-dev-only manifest used by `pac pages upload` to compute incremental uploads. Microsoft's own docs say this file "is designed to be used by developers for deploying locally ... and should be added to git ignore list." It's read-only when connected to its matching environment and isn't meant for cross-environment diffing. |
| `.powerpages-site/web-files/` | ❌ No | The built SPA bundle (hashed `main.*.js`/`.css`, chunk files, `asset-manifest*.json`, duplicated `index_*.html` variants) copied in by `pac pages download` after every build/upload cycle. Fully regenerated from `vmbso-spa-v2/build` (Vite output) at deploy time — tracking it just produces hash-churn noise on every commit. |
| `vmbso-spa-v2/build/`, root `dist/` | ❌ No | Vite build output (`outDir: 'build'` in `vite.config.ts`). `dist/` at the repo root was stray leftover output, unreferenced by any script. |

**Fixed in this pass:** `vmbso-spa-v2/.gitignore` had `dist` (a leftover from before the Vite migration changed `outDir` to `build`), so `build/` was never actually ignored and had been slipping into git. Added `build` to the ignore list, plus rules for `web-files/` and the per-environment `.portalconfig/*-manifest.yml` files (explicitly keeping the shared `manifest.yml`).

## Environment variables for site settings

Power Pages supports backing a site setting with a Dataverse **environment variable** instead of a static value (GA since March 2025, enhanced data model only). The site setting's `source` becomes `1`, and the setting resolves to whichever value is configured for the environment currently running — so the same site-setting YAML is identical across dev/test/prod, while the *value* varies per environment.

Reference: [Use environment variables with site settings](https://learn.microsoft.com/power-pages/configure/environment-variables-for-site-settings)

### Why we added these

A comparison of all 148 site settings between the **dev** and **test** Dataverse environments (via `pac pages download-code-site` against each org) found exactly one real gap: the site's only configured identity provider, `Authentication/OpenIdConnect/EntraExternalID_3`, had **identical hardcoded values in both environments** — including a `RedirectUri` pointing at test's own portal hostname (`https://customerportal-test.powerappsportals.com/...`). Since dev's actual portal URL differs, this was a live sign-in risk on dev, not a stylistic ALM improvement.

### Environment variables created

Created in the dev environment's Power Pages Management app, using a `vmbso_` schema-name prefix (independent of the `actum_` prefix used by the org's custom Dataverse tables — env var schema names don't need to match table prefixes, this is just the naming convention chosen for these):

| Site setting | Env var schema name | Display name | Type |
|---|---|---|---|
| `Authentication/OpenIdConnect/EntraExternalID_3/Authority` | `vmbso_entraexternalid_authority` | VMBSO Portal EntraExternalID Authority | String |
| `Authentication/OpenIdConnect/EntraExternalID_3/ClientId` | `vmbso_entraexternalid_clientid` | VMBSO Portal EntraExternalID ClientID | String |
| `Authentication/OpenIdConnect/EntraExternalID_3/MetadataAddress` | `vmbso_entraexternalid_metadataaddress` | VMBSO Portal EntraExternalID MetadataAddress | String |
| `Authentication/OpenIdConnect/EntraExternalID_3/RedirectUri` | `vmbso_entraexternalid_redirecturi` | VMBSO Portal EntraExternalID Redirect URI | String |
| `Authentication/OpenIdConnect/EntraExternalID_3/PostLogoutRedirectUri` | `vmbso_entraexternalid_postlogoutredirecturi` | VMBSO Portal EntraExternalID PostLogout Redirect | String |

Note: the schema names deliberately drop the `_3` provider-slot suffix since only that slot is in use — the link to the site setting is by lookup, not by name-matching, so this is purely a readability choice.

No `ClientSecret` setting exists for this provider — it's configured as a public/PKCE client, so there's no secret-typed value to manage.

Slots `EntraExternalID_1` and `_2` are unused (empty caption, no values) and were left as static settings.

### Related incident: SPA build had test's Authority baked in, breaking prod login

While prod was being prepared for go-live, the custom login button (SPA-rendered, POSTing to `/Account/Login/ExternalLogin`) returned 401, while the server-rendered `/Account/Login` page's own button worked fine. Root cause: the SPA's `provider` form field is sourced from `REACT_APP_ENTRA_PROVIDER` in `vmbso-spa-v2/.env.production` — a **build-time** value — and it still pointed at test/UAT's Authority (`vmbsocustomerportaluat.ciamlogin.com/...`) instead of prod's (`vmbsocustomerportal.ciamlogin.com/...`). The server-rendered page never has this problem because Power Pages generates its button from the live site setting at request time; the SPA bundle had no equivalent and had to be told the value at build time instead.

Immediate fix: corrected `.env.production` and redeployed. Follow-up fix (see next section): removed the build-time coupling entirely so this class of bug can't recur.

## Runtime config for the SPA (`actum_publicconfig` table)

The env-var-backed site settings above solve per-environment config for **server-side** OWIN auth handling. They don't help the **SPA's own client-side code**, which also needs the Entra provider identifier (to POST it as the `provider` field) and the GA4 measurement ID — and Web API only exposes Dataverse tables, not site settings, so there's no way for the SPA to read a site setting directly at runtime.

Previously these lived in `vmbso-spa-v2/.env.production` (`REACT_APP_ENTRA_PROVIDER`, `REACT_APP_GOOGLE_ANALYTICS_ID`) — build-time values baked into the compiled bundle. That's what caused the incident above: promoting the same build to a new environment silently carried over the wrong value, and fixing it required a rebuild + redeploy.

**Fix:** a small dedicated Dataverse table, `actum_publicconfig` (key/value: `actum_name` / `actum_value`), exposed to the SPA via Web API and read once at app bootstrap — so the same build works unchanged across dev/test/prod, and changing a value is just editing a Dataverse row (maker portal), no rebuild.

| Piece | Detail |
|---|---|
| Table | `actum_publicconfig` — `actum_name` (primary/key), `actum_value` (text, 500 chars) |
| Web API site settings | `Webapi/actum_publicconfig/enabled`, `Webapi/actum_publicconfig/fields` (`actum_publicconfigid,actum_name,actum_value`) |
| Table permission | `Public-Config.tablepermission.yml` — Global scope, **read-only**, granted to **both** Anonymous Users and Authenticated Users (the Login page needs the Entra provider identifier before the user is authenticated) |
| SPA read path | `dataverseService.publicConfig.getAll()` → `publicConfigService.loadPublicConfig()`, awaited in `main.tsx` before GA init and `initializeTranslations()` — populates `config.auth.providerScheme` and `config.analytics.googleAnalyticsId` in `powerPages.config.ts` |
| Keys currently in use | `EntraProviderIdentifier` (Entra External ID Authority URL), `GoogleAnalyticsId` (GA4 measurement ID, optional — the app degrades gracefully with GA fully disabled if this row is missing/empty) |

Current state: table created in the **dev** environment only, seeded with placeholder values (`TODO_SET_DEV_ENTRA_AUTHORITY_URL` / `TODO_SET_DEV_GA_MEASUREMENT_ID`). Not yet added to a Dataverse solution.

### How to add more environment variables later

1. Power Pages Management app → **Site Settings** → open the setting → **Source** → **Environment Variable**.
2. **New Environment Variable Definition** → Schema Name (`vmbso_<setting_name>`), Display Name, Type (String unless it's a Key Vault-backed secret), optional Default Value.
3. Save, then open the definition → **Values** → **New Environment Variable Value** → set the current environment's value.
4. Repeat per environment once the site/solution is deployed there — each org's Management app has its own **Values** list against the same shared definition that travels with the solution.
